Distributed Systems Cheatsheet

Unit 1: Introduction, Architectures & Design Issues

Distributed vs Centralized System

  • Def: independent computers connected by a network that appear to users as one coherent system.
  • Key idea: share resources and coordinate only by message passing.
  • Distributed: no shared clock/memory, multiple points of failure but no single one, scalable, concurrent, transparency needed.
  • Centralized: one server, single point of failure, easy control and consistency, limited scaling.
Ex (hospital, 5 cities): single HQ server = all hospitals lose records on failure. Distributed replicas = higher availability, resource sharing, but need coordination/consistency.

Goals / Characteristics

  • Resource sharing (files, CPU, devices)
  • Openness (standard, published interfaces)
  • Scalability (size, geography, administration)
  • Transparency: access, location, migration, relocation, replication, concurrency, failure
  • Fault tolerance & availability: redundancy, failure detection, failover
  • Heterogeneity: hardware, OS, network, language, data format
  • Concurrency and Security (confidentiality, integrity, availability)
Ex (offices in Pune/Delhi/Bengaluru): shared docs = resource sharing; add office easily = scalability/openness; users unaware of location = location transparency; local failure tolerated = replication.

Architectural Models

  • Client-server: clients request, central server serves. Simple, centrally managed, server is bottleneck/SPOF. Fits exam system, student-record system.
  • Peer-to-peer: every peer is client and server. Scales, no SPOF, harder discovery/security/control. Peer discovery, lookup (index/flooding/DHT), direct transfer. Fits file sharing.
  • Multi-tier: Presentation (UI, login screens), Application (business logic, order, payment coordination), Data (database). Each tier scales and is maintained independently. Fits admission portal, retailer.
  • Hybrid: central index/tracker + P2P transfer; used in video conferencing and content distribution.
Ex: Retailer sale traffic: replicate stateless app tier behind load balancer, cache in front of DB, scale tiers separately.

Middleware

  • Def: software layer between OS/network and applications.
  • Key idea: hides heterogeneity, gives uniform communication (RPC, messaging, objects).
  • Hides: OS, hardware, network protocol, language differences, data representation (marshalling).
  • Not hidden: application semantics, business-level data meaning, performance, partial failures.
Ex (Java/Linux + .NET/Windows + Python merger): use common protocol and format (REST/JSON, gRPC, message queue) instead of rewriting.

Heterogeneity Levels

  • Hardware: byte order, word size
  • OS: APIs, file systems
  • Communication: protocols, interfaces
  • Data: formats, encodings (use XDR/JSON/XML/Protobuf)

Design Issues in Large Systems

  • Conflicts: scalability vs consistency, transparency vs performance, security vs speed, fault tolerance vs cost.
  • Cloud app: balance scalability, availability, performance via tiers, replication, caching.

Distributed Multimedia & WAN Performance

  • Multimedia needs QoS: bandwidth, low delay, low jitter, synchronization of audio/video.
  • Problems: buffering, bandwidth variation, server load, node failure.
  • Solutions: adaptive bitrate, buffering, CDN, replicated servers, load balancing, multicast/hybrid P2P.
  • WAN factors: latency (distance), bandwidth, congestion, packet loss, server load, routing, consistency overhead.
Ex (live sports streaming): centralized = bottleneck; multi-tier = better; distributed CDN = best scalability, latency, fault tolerance but harder synchronization.

Fault Tolerance vs Availability

  • Availability = fraction of time service is up. Fault tolerance = continue correctly despite faults.
  • Redundancy + failure detection (heartbeat/timeouts) + failover.
  • Network partition: cannot sync updates, so trade consistency for availability (CAP).

Healthcare / Bank Requirements

  • Security: authentication, encryption, access control. Scalability: tiers, replication. Fault tolerance: replicated servers. Consistency: transactions/locking for concurrency.

Unit 2: Communication

Basic Communication Model

  • Elements: sender, receiver, message, channel (+ protocol).
  • Key idea: processes interact only by exchanging messages.
Ex: browser (sender) sends HTTP request (message) over TCP (channel) to web server (receiver).

Remote Procedure Call (RPC)

  • Def: call a remote procedure as if local.
  • Key idea: stubs hide the network.
  • Sequence: client calls client stub → marshal (serialize) parameters → send via runtime/network → server stub unmarshals → server executes procedure → result marshalled → returned → client stub unmarshals → returns to caller.
  • Parameters: pass by value (copy); references need deep copy or global reference; use IDL/XDR for representation.
  • Error handling: timeout, retry, unique request ID, duplicate detection (server stores IDs/results), idempotent operations.
  • Semantics: at-least-once, at-most-once, exactly-once (hard).
Ex (bank fund transfer): response lost → client retries with same request ID → server detects duplicate and returns stored result, so no double debit.

Message-Oriented Communication

  • Def: async messages via queues/brokers (producer → queue → consumer).
  • Key idea: decouples sender and receiver in time; no need to be up simultaneously.
  • Models: sync/async, transient/persistent. Delivery: ack, at-least-once, ordering. Examples: RabbitMQ, Kafka, MQ.
Ex: Order service publishes "OrderPlaced" to queue; notification, inventory and shipping services consume independently.

Stream-Oriented Communication

  • Def: continuous, time-dependent media flow (audio/video).
  • Key idea: timing matters as much as data.
  • Needs: QoS (bandwidth, delay, jitter), playout buffering, jitter control, A/V synchronization (timestamps), adaptive bitrate, UDP/RTP/RTCP.
  • Under varying bandwidth: adapt quality, buffer, FEC/retransmit selectively.
Ex: Conferencing: control messages by RPC/messages, audio and video as separate streams synchronized via timestamps.

Peer-to-Peer Messaging

  • Direct peer message exchange: discovery (tracker/DHT) → lookup → connect → transfer.
  • Signaling server needed across NAT/different networks.

WebRTC

  • Def: browser real-time audio/video/data, peer to peer.
  • Signaling (WebSocket/HTTP, not defined by WebRTC) exchanges: SDP offer (caller) → SDP answer (callee) → ICE candidates both ways.
  • ICE connectivity checks pick best path; STUN discovers public address; TURN relays if direct fails.
  • Then DTLS-SRTP media (audio/video tracks) and RTCDataChannel (text/files).

Choosing a Mechanism

  • RPC: low-latency request-response (meeting creation, balance query).
  • Message-oriented: async alerts/notifications, intermittent links, reliable.
  • Stream: live audio/video.
  • P2P/WebRTC: direct data/media, scales with users, reduces server load.
Ex (telemedicine): booking → RPC; notifications → message queue; consultation → WebRTC stream; record update → RPC with duplicate detection.
Ex (emergency platform): RPC for patient status requests, queue for alerts (survive intermittent links), stream for live video.

Unit 3: Clocks, Synchronization, Election & Mutual Exclusion

Physical Clock Terms

  • Offset = difference between two clocks at an instant. Skew = difference in rate. Drift = rate error × time.
  • Physical clocks: real-time, need sync, ms accuracy. Logical clocks: ordering only, no real time.
Ex: A=10:00:00, B=10:00:07, B gains 0.002 s/s. Initial offset 7 s; extra after 1 h = 0.002×3600 = 7.2 s; total 14.2 s, B ahead.
Drift/day: 0.0001×86400 = 8.64 s; 0.01×86400 = 864 s; ratio = 100.

Cristian's Algorithm

  • Client asks time server; T_client = T_server + RTT/2. Accuracy ± (RTT/2 − min delay).
  • Limits: single server = SPOF (if down, no sync), asymmetric delay error.
Ex: send 10:00:00.000, receive 10:00:00.400, T_server=10:00:00.250. RTT=400 ms; one-way=200 ms; set 10:00:00.450; uncertainty ±200 ms.
Ex: delays 1 s out, 5 s back, T=12:00:10. RTT=6 s; estimate 12:00:13; true 12:00:15; error 2 s (client behind).
Ex: 10:25:12 → 10:25:18, T=10:25:15. RTT=6 s; delay 3 s; set 10:25:18; differs since delays may be asymmetric.

Berkeley Algorithm

  • Coordinator polls machines, averages (ignores outliers), sends each adjustment (not absolute time). No UTC needed; internal sync.
  • Limits: coordinator failure, needs election.
Ex: average 10:00:15, machine shows 10:00:20 → adjust −5 s.

NTP

  • Hierarchical strata, UTC-connected, internet; accuracy ~ms (LAN) to tens of ms (WAN), so suitable for ms-level needs.
  • offset θ = ((t1−t0)+(t2−t3))/2, delay δ = (t3−t0)−(t2−t1)
Ex: t0=50, t1=90, t2=95, t3=130: θ=(40−35)/2=2.5 ms; δ=80−5=75 ms; θ>0 so client is behind server by 2.5 ms.

Time Dissemination Delays

  • Signal generation/propagation, receiver processing, network transit, OS interrupt/scheduling, clock-set latency.

Lamport Logical Clock

  • Rules: increment before each event; send with timestamp; on receive C = max(local, msg) + 1.
  • Clock condition: a→b ⇒ C(a) < C(b); converse false, so cannot detect concurrency.
Ex (P1→P2→P3→P2→P1): m1=1; P2 recv=2, m2=3; P3 recv=4, m3=5; P2 recv=6, m4=7; P1 recv=8. Final P1=8, P2=7, P3=5.
Ex (bank): M1=1; P2 recv 2, M2=3; M3=2; P3 recv M2=4, M3=5, M4=6; P1 recv=7. Final P1=7, P2=3, P3=6.
Ex (local events): P1 local 1, m1=2; P2 recv 3, local 4, m2=5; P3 recv 6, local 7, m3=8; P1 recv 9, m4=10; P3 recv 11.

Vector Clock

  • Vector of n counters. Local event: increment own; receive: element-wise max then increment own.
  • V1<V2 iff all ≤ and one < (happened-before); otherwise concurrent. Captures causality (Lamport doesn't).
Ex: [2,1,0] vs [1,2,0] → concurrent. [3,2,1] vs [4,2,2] → first happened before second.
Cart: [1,0,1] vs [2,0,0] concurrent → keep both versions, merge (union), new clock [2,0,1].

Lamport Ordering (Healthcare)

  • Order prescription, lab, allergy updates by (timestamp, process ID) → consistent total order across replicas.

Bully Election

  • Highest ID wins. Process noticing failure sends ELECTION to higher IDs; any alive replies OK and takes over; highest alive broadcasts COORDINATOR.

Ring Election

  • Logical ring; ELECTION message collects IDs as it circulates; initiator picks highest, sends COORDINATOR around ring.
Ex: P5 (coordinator) fails, P2 detects. Bully: P2→P3,P4,P6; P3,P4 reply, P4 continues, P6 wins. Ring: list [2,3,4,6] circulates, 6 chosen.

Lamport Mutual Exclusion

  • Broadcast REQUEST(ts,id) to all; every process replies (REPLY) and queues request; enter CS when own request is at head of queue and replies from all received; on exit broadcast RELEASE. Cost 3(N−1) messages.
Ex: P1, P2 request with equal timestamp → tie broken by smaller process ID, so P1 enters first; P2 enters after P1's RELEASE. Flash-sale: lowest (ts,id) data center buys last item, preventing overselling.

Comparison

  • Physical: real time, needs sync. Logical: ordering only.
  • Cristian: server-based, needs time server. Berkeley: averaging, no UTC.
  • Lamport: single integer, partial info. Vector: n integers, detects concurrency.

Unit 4: Distributed File Systems, Web & Cloud Paradigms

DFS vs Conventional File System

  • DFS: files across many nodes, network access, replication, location transparency, scalable, fault tolerant. Conventional: single machine/disk, local access, limited capacity, single failure point, no network latency.
Ex: centralized file server limits storage, throughput and availability; DFS spreads and replicates data.

HDFS / Hadoop

  • NameNode (metadata), DataNodes (blocks, default 128 MB), 3 replicas, heartbeats.
  • Replica placement: 1st on writer's node, 2nd on a different rack, 3rd on another node in that rack → survives node or rack failure, reduces cross-rack traffic.
  • MapReduce: computation moves to data (data locality); map → shuffle → reduce.
Ex (log analysis): web layer uploads logs → HDFS → MapReduce/Spark → results served by web app.

Distributed Objects

  • Remote objects via proxy/skeleton (RMI, CORBA). Differences from local: latency, partial failure, no shared memory, need object references and serialization.
Ex: Customer/Account/Transaction on different machines → coarse-grained calls, handle failures and transactions.

Web, CDN & Cloudflare

  • Single origin = distance latency + overload. Fix: load balancer, caching, replicated servers, CDN.
  • Cloudflare: edge caching, DNS, DDoS/WAF; cached static content served from nearest edge → lower latency, less origin load.
Ex: Pune/Delhi/London users on one origin: far users slow; edge caches cut response time.

Megaport

  • Private multi-cloud/data-center connectivity (Software-defined) with predictable latency, controllable network, high availability vs public internet. Cloudflare = edge delivery/security; Megaport = private interconnect.

AWS

  • Compute: EC2, Auto Scaling, ELB. Storage: S3 (objects), EBS, RDS. Network: VPC, Route 53, CloudFront.
Ex: EC2 behind ELB + S3 + RDS in a VPC with Auto Scaling for variable load.

Kubernetes

  • Pod (smallest unit), Deployment/ReplicaSet (desired replicas), Service (stable IP, load balancing), Scheduler (places pods), kubelet, etcd, HPA (autoscale).
  • Pod fails → ReplicaSet creates replacement; Service routes to healthy pods. Node fails → pods rescheduled on other nodes (limits: stateful data, detection delay, capacity).
  • Single pod = SPOF and no scaling.
Ex: 3 replicas: one pod fails → Service stops routing to it, Deployment launches new pod; availability maintained.

Serverless

  • Event-driven functions (AWS Lambda), auto-scale to zero, pay per use. Good for spiky, short tasks (file processing: S3 upload → Lambda → store result).
  • Less suitable: long-running, steady high load, low-latency (cold starts), vendor lock-in, state.
Ex (result portal, 2-hr peak): serverless best for spiky load; Kubernetes for steady complex services; servers wasteful.

Object Storage vs DFS

  • Object storage (S3): flat namespace, HTTP API, huge scale, durable, cheap, no POSIX. DFS: hierarchical, file semantics, analytics (HDFS).

Monolith → Distributed Migration

  • Monolith: scaling and failure limits. Use web services/tiers first, containers/Kubernetes for orchestration, serverless for event tasks, replicated storage.
Ex (college system): load balancer + replicated app servers (K8s) + HDFS/DFS storage + CDN caching.
