DevOps Cheat Sheet

1. DevOps culture and models

Purpose

  • Remove the wall of confusion between Dev and Ops for fast, safe delivery.
  • CAMS: Culture, Automation, Measurement, Sharing.
  • Three Ways: Flow (small batches, WIP limits), Feedback (tests, monitoring), Continual learning (blameless, chaos, game days).

Tools and metrics

  • DORA metrics: deployment frequency, lead time, change failure rate, time to restore.
  • Evolution: 2008 Agile Infrastructure, 2009 DevOpsDays, then CI/CD, DevSecOps, SRE, platform engineering.
  • Chaos Monkey (Netflix): kills instances to test resilience.

Steps

  • Diagnose with CAMS, automate the pipeline, measure DORA, share via retros.
Example: Etsy moved from rare, risky releases to many daily deploys using automation and shared dashboards.

2. Agile, Scrum and Kanban

Purpose

  • Agile builds software in short cycles; DevOps extends it to operations.

Key differences

  • Agile scope: development. DevOps scope: idea to production and operation.
  • Scrum: fixed sprints, roles, velocity. Kanban: continuous flow, WIP limits, cycle time.
  • Kanban suits ops and support work; Scrum suits planned features.

Steps

  • Add pipeline and monitoring work to the sprint backlog, and extend the Definition of Done with tests, scan and deployable.
Example: A support team limits In Progress to 3 cards and sees reviews pile up, so it adds reviewers.

3. Version control with Git

Purpose

  • Track changes, enable parallel work and collaboration. Distributed, fast, SHA-1 integrity.
  • Three areas: working directory, staging area, repository.

Tools

  • Git (local), GitHub, GitLab, Bitbucket (hosting). SVN is the centralized alternative.
  • Branching: Git Flow, GitHub Flow, trunk-based (best for many releases a day).

Commands

  • git init, git clone url, git status, git diff, git log --oneline --graph
  • git add ., git commit -m "msg", git push, git fetch, git pull
  • git branch, git switch -c feat, git merge feat, git rebase main (never on shared branches)
  • git reset --soft|--mixed|--hard (rewrites history), git revert sha (safe undo)
  • git stash, git stash pop, git cherry-pick sha, git tag -a v1 -m "x"
  • Conflict: edit markers, git add, git commit; cancel with git merge --abort. Use .gitignore for target/, __pycache__/, .env
Example: Hotfix while a feature is half done: stash, branch from main, fix, merge, then stash pop. Leaked AWS key: rotate it first, then purge history.

4. GitHub and GitHub Actions

Purpose

  • Hosting, pull requests, code review and workflow automation. Git is the tool; GitHub is the service.

Tools

  • Pull requests, branch protection, CODEOWNERS, Issues (tasks), Projects (boards), fork vs clone.
  • Actions: events (push, pull_request, schedule, workflow_dispatch), jobs, runners, steps (uses, run).

Steps

  • Jobs run in parallel; needs: makes them sequential. strategy.matrix tests many OS and versions.
Example: on: [push] then runs-on: ubuntu-latest with steps uses: actions/checkout@v4 and run: npm test.

5. CI/CD concepts

Purpose

  • CI: merge often with automatic build and test. Continuous Delivery: always releasable, manual approval to production. Continuous Deployment: every passing change goes live.

Pipeline stages

  • Code, build, test, release (artifact), deploy, monitor. Pipeline as Code keeps it in Git.
  • Promotion: dev, staging, production with quality gates and manual approval.

Steps

  • Build once, promote the same artifact, fail fast, and notify on failure.
Example: A bank delivers daily but a manager approves production; a streaming site deploys every passing commit.

6. Jenkins

Purpose

  • Automation server for CI/CD. Controller schedules; agents (labelled) run builds.

Tools

  • Freestyle job, declarative Jenkinsfile, shared libraries, Credentials plugin, post actions (email, Slack).
  • Triggers: pollSCM, cron, GitHub webhook.

Steps

  • Install JDK and Jenkins, open port 8080, unlock, install suggested plugins.
  • Jenkinsfile: pipeline { agent { label 'linux' } stages { stage('Build'){ steps { sh 'mvn package' } } } }
  • Troubleshoot with Console Output and build history.
Example: A push triggers a webhook, Jenkins builds, tests, builds a Docker image and updates Kubernetes.

7. Maven, SonarQube, Nexus

Purpose

  • Maven builds Java projects. SonarQube checks quality. Nexus or Artifactory stores artifacts.

Tools

  • pom.xml, JUnit with Surefire plugin, multi-module parent POM, quality gate (coverage, code smells).

Commands

  • Lifecycle: validate, compile, test, package, verify, install, deploy.
  • mvn archetype:generate, mvn clean package, mvn test, mvn deploy
  • Layout: src/main/java, src/test/java, target/
Example: waitForQualityGate abortPipeline fails the build when coverage drops below the threshold.

8. GitLab CI

Purpose

  • Built-in CI/CD in GitLab, configured by .gitlab-ci.yml.

Tools

  • Stages, jobs, artifacts, cache, rules, environments, GitLab Runner.

Steps

  • stages: [build, test, deploy] then jobs with script:.
  • Register a runner: gitlab-runner register with URL and token.
Example: Deploy to staging from develop automatically; production from main with when: manual.

9. Docker

Purpose

  • Package an app and its dependencies as a portable container. Lighter than VMs because the kernel is shared.

Architecture

  • Client, daemon, images (read-only), containers (running), registry (Docker Hub, ECR).
  • Dockerfile: FROM, WORKDIR, COPY, RUN, EXPOSE, USER, CMD. Multi-stage builds and .dockerignore keep images small.

Commands

  • docker pull nginx, docker run -d -p 8080:80 --name web nginx, docker ps, docker stop web, docker rm web
  • docker build -t app:1.0 ., docker push user/app:1.0, docker exec -it web sh, docker logs web
  • docker volume create v, -v v:/data, --memory 256m, docker network create n (name resolution between containers)
Example: MySQL data kept in volume dbdata survives container removal and image upgrades.

10. Docker Compose and microservices

Purpose

  • Run multi-container apps from one file. Microservices split an app into small services, each with its own database.

Tools

  • docker-compose.yml: services, networks, volumes, environment, depends_on.
  • Communication: REST for direct calls, messaging (Kafka, RabbitMQ) for events. API gateway as single entry.

Commands

  • docker compose up -d, docker compose down
  • Challenges: no cross-service transactions (use Saga), eventual consistency.
Example: WordPress service plus MySQL service with a dbdata volume; food-delivery split into order, payment and delivery services.

11. Kubernetes

Purpose

  • Orchestrates containers: scheduling, scaling, self-healing, rolling updates.

Architecture

  • Control plane: API server, etcd, scheduler, controller manager. Node: kubelet, kube-proxy, container runtime.
  • Objects: Pod, ReplicaSet, Deployment, Service (ClusterIP, NodePort, LoadBalancer), ConfigMap, Secret, PVC, Namespace.
  • HPA: desired = ceil(current x currentCPU / targetCPU). Liveness restarts; readiness gates traffic.

Commands

  • kubectl get nodes|pods|svc, kubectl apply -f x.yaml, kubectl describe pod p
  • kubectl logs p, kubectl exec -it p -- sh, kubectl delete pod p, kubectl create namespace dev
  • kubectl rollout status|history|undo deploy/web, kubectl autoscale deploy web --min=2 --max=10 --cpu-percent=50, kubectl expose deploy web --type=NodePort --port=80
Example: 4 pods at 80% CPU with a 50% target scale to ceil(4 x 80 / 50) = 7 pods.

12. Deployment strategies

Purpose

  • Release with little or no downtime and a safe rollback.

Strategies

  • Recreate: stop old, start new (downtime).
  • Rolling: replace gradually (maxSurge, maxUnavailable).
  • Blue-green: two environments, switch traffic, instant rollback.
  • Canary: 10% of users first, metrics decide promote or rollback.
  • Feature toggles: separate deployment from release.
Example: v2 shows 3% errors against 0.5% in v1 during canary, so traffic goes back to v1.

13. Terraform and IaC

Purpose

  • Declarative Infrastructure as Code: idempotent, versioned, repeatable, self-documenting. Supports immutable infrastructure.

Tools

  • Provider, resource, variables.tf, outputs.tf, modules (pin versions), state.
  • Remote state: S3 plus DynamoDB lock. Environments: workspaces or separate directories.
  • Drift: scheduled terraform plan. Secrets: Vault, Secrets Manager, sensitive variables.

Commands

  • terraform init, plan, apply, destroy, fmt, validate
Example: provider aws region ap-south-1, then an aws_s3_bucket resource, applied after reviewing the plan.

14. Ansible and configuration management

Purpose

  • Agentless configuration over SSH. Terraform provisions; Ansible configures.

Tools

  • Inventory (groups), playbook (YAML), module, task, role, handler (runs on change).

Commands

  • ansible all -i inventory.ini -m ping
  • ansible-playbook -i inventory.ini site.yml
  • Tasks: apt: name=apache2 state=present, service: name=apache2 state=started, user: name=devuser
Example: One playbook with an nginx role configures 50 web servers and restarts Nginx only when the config changes.

15. Cloud: AWS, RDS and Aurora

Purpose

  • Rent infrastructure on demand. IaaS (EC2), PaaS (Elastic Beanstalk, RDS), SaaS (WorkMail).

Tools

  • Equivalents: EC2 / Azure VM / Compute Engine; S3 / Blob / Cloud Storage; RDS / Azure SQL / Cloud SQL; EKS / AKS / GKE.
  • RDS: Multi-AZ (failover), read replicas (scale reads, DR), automated backups, snapshots.
  • Aurora: 1 writer plus readers, shared storage in 3 AZs, fast failover.

Steps

  • RDS console: Create database, choose engine, set credentials, class, storage, VPC and security group, backups, then Create.
  • Migration: assess, rehost, then replatform; EC2 + RDS + S3.
Example: A shop writes to the Aurora writer and sends product searches to readers during a sale.

16. Prometheus and Grafana

Purpose

  • Collect metrics (pull model) and visualize them.

Tools

  • Prometheus server, exporters (Node Exporter), Pushgateway, Alertmanager (group, inhibit, silence), Grafana dashboards and variables.
  • Metric types: Counter, Gauge, Histogram, Summary.
  • Methods: Golden Signals (latency, traffic, errors, saturation), RED for services, USE for infrastructure.

Commands and steps

  • prometheus.yml: scrape_configs: - job_name: app, static_configs: targets: ['host:8080']
  • PromQL: rate(http_requests_total[5m]), sum by (job)(rate(...)), histogram_quantile(0.95, ...)
  • Grafana: add Prometheus data source, build panels, add alerts.
Example: Alert when CPU stays above 80% for 5 minutes, routed to Slack.

17. Centralized logging: ELK

Purpose

  • Collect all logs in one place for search and analysis.

Tools

  • Filebeat ships logs; Logstash parses (input, grok filter, output); Elasticsearch stores (index, document, shard); Kibana searches and charts (data views).
  • Log levels: DEBUG, INFO, WARN, ERROR. Use JSON logs with correlation IDs.

Steps

  • Create a data view, search with KQL such as status >= 500, chart counts by service.
Example: Searching one trace ID in Kibana shows a failed order across five services.

18. Observability and tracing

Purpose

  • Monitoring says that something is wrong; observability helps find why.

Tools

  • Three pillars: metrics, logs, traces. Tracing tools: Jaeger, Zipkin, OpenTelemetry.
  • Trace is a whole request; span is one unit of work in it.

Steps

  • Metrics find where, traces find the slow service, logs explain what.
Example: A 3-second checkout trace shows 2.8 seconds in the inventory database query.

19. SRE: SLI, SLO, SLA and error budget

Purpose

  • Treat operations as software engineering to balance reliability and speed.

Key points

  • SLI measured value, SLO internal target, SLA customer contract. Error budget = 100% minus SLO.
  • Budget gone: freeze features and fix reliability. Reduce toil by automation.
  • Availability = MTBF / (MTBF + MTTR). Metrics: MTTD, MTTA, MTTR.
  • On-call: PagerDuty or Opsgenie, escalation, alert on symptoms to reduce fatigue.

Numbers

  • 99.9% per month (43,200 min) = 43.2 min; 99.5% = 216 min (3.6 h).
  • Per year: 99% = 3.65 days, 99.9% = 8.76 h, 99.99% = 52.6 min.
Example: A 60-minute outage uses the full 43.2-minute budget, so releases pause.

20. Incident management and post-mortem

Purpose

  • Restore service fast and learn without blame.

Steps

  • Detect, triage (severity), assign Incident Commander, communicate, mitigate (rollback or failover), resolve, close.
  • Post-mortem: summary, impact, timeline, root cause, what went well or badly, action items with owners.
Example: A primary database crash is handled by promoting the replica in 10 minutes while the commander posts updates.

21. DevSecOps

Purpose

  • Shift left: add security checks early in the pipeline.

Tools and placement

  • Secrets detection (gitleaks) at commit; SAST (SonarQube, CodeQL) after build; dependency scan (Snyk, OWASP Dependency-Check); image scan (Trivy); DAST (OWASP ZAP) in staging.
  • Keep secrets in Vault, Secrets Manager, Jenkins Credentials or Kubernetes Secrets, never in code.

Commands

  • trivy image app:1.0, gitleaks detect
Example: The build fails because a library has a critical vulnerability.
