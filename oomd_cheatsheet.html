OOMD Cheat Sheet

1. Object-Oriented Thinking and Architectural Thinking

  • Object-oriented thinking: model the domain as objects with data and behaviour, not as functions and data apart.
  • Architectural thinking: decide the big structure first (layers, services, data stores), then the classes inside.
  • Object responsibilities: each object should know what it needs and do what it owns.
  • Class: blueprint with attributes and operations.
  • Object: an instance of a class with its own state.
  • Encapsulation: hide data; change it only through methods.
  • Abstraction: show only essential features.
  • Inheritance: child class reuses parent class (is-a).
  • Polymorphism: same method name, different behaviour per class.
Example: Shape.area() gives different results for Circle and Rectangle.

2. UML Modelling

  • UML is a standard visual language to specify, visualize and document software.
  • Structural diagrams: class, object, component, deployment, package.
  • Behavioral diagrams: use case, sequence, communication, activity, state machine.
  • Class box: name, attributes, operations. Visibility: + public, - private, # protected.

5. SOLID Principles

  • S Single Responsibility: a class has one reason to change.
  • O Open/Closed: extend with new classes, do not edit working code.
  • L Liskov Substitution: a subclass can replace its parent without breaking behaviour (Square must not break Rectangle rules).
  • I Interface Segregation: many small interfaces, not one big one.
  • D Dependency Inversion: depend on interfaces, not concrete classes.

6. GRASP Principles

  • Information Expert: give the job to the class that holds the data.
  • Creator: class A creates B if A contains, records or closely uses B.
  • Controller: a non-UI class handles a system event.
  • Low Coupling: keep links between classes few.
  • High Cohesion: keep each class focused.
  • Polymorphism: use subclasses instead of type checks.
  • Pure Fabrication: invent a helper class for clean design (e.g. StudentRepository).
  • Indirection: add a middle object to reduce direct links.
  • Protected Variations: hide points of change behind a stable interface.

7. Cohesion and Coupling

  • Cohesion: how related the work inside a class is. Aim for high.
  • Cohesion types (weakest to strongest): coincidental, logical, sequential, communicational, functional.
  • Coupling: how much classes depend on each other. Aim for low.
  • Coupling types (tightest to loosest): content, common, control, stamp, data.

8. CRC Cards and Responsibility Assignment

  • CRC = Class, Responsibilities, Collaborators. One index card per class.
  • Write what the class knows and what it does, then list the classes it works with.
  • Check for one clear job per card (high cohesion) and few collaborators (low coupling).

9. UML Modelling Tools

  • draw.io: drag and drop, free, good for quick diagrams.
  • StarUML: full UML support, good for detailed models.
  • Mermaid.js: text code, stores in Git and shows clear diffs.

10. Domain-Driven Design (Self Study)

  • Entity: has identity (customerId).
  • Value object: no identity, defined by values (Address, Money).
  • Aggregate root: single entry point to a group of objects (Order).
  • Bounded context: a boundary where one model applies (Order, Inventory).

11. Architecture Decision Records (ADR)

  • A short record of one decision and why it was made.
  • Sections: Title, Status, Context, Decision, Alternatives Considered, Consequences.
  • Templates: Nygard (simple) and MADR (adds decision drivers and pros and cons).
  • Store in Git (for example docs/adr), numbered, never reused.

12. Database Design from Class Models

  • Each class becomes a table. Each attribute becomes a column. Identity becomes the primary key.
  • One-to-many: foreign key on the "many" side.
  • Many-to-many: junction table holding both keys.
  • ER model vs class model: ER shows data only; class model also shows behaviour.

13. Normalization

  • 1NF: each cell holds one atomic value (no lists).
  • 2NF: no partial dependency on part of a composite key.
  • 3NF: no transitive dependency (non-key depends on non-key).
  • BCNF: every determinant is a super key.

14. ORM, DAO and Repository

  • ORM (e.g. Hibernate): maps objects to tables, so code works with objects.
  • N+1 problem: one query for the list plus one per item. Fix with join fetch or batch fetching.
  • DAO: low-level data access for one table.
  • Repository: domain-level collection of objects used by the service layer.

15. NoSQL Design Concepts

  • Document: flexible JSON-like records (catalogue with varied fields).
  • Key-value: fast access by key (shopping cart by session id).
  • Column: wide rows, suited to large write volumes.
  • Graph: nodes and links (customers also bought).
  • Start from access patterns, then choose the model.

16. Distributed Databases and CAP

  • Partitioning (sharding): split data across servers (range, hash, directory).
  • Replication: copies for reads and failover. Replicas can lag behind the primary.
  • CAP theorem: during a network partition, choose Consistency (CP) or Availability (AP).
  • Read-your-own-writes: after a write, read from the primary for a short time.

17. Indexing Strategies

  • Index columns used in WHERE, JOIN and ORDER BY.
  • Composite index: column order matches the query (customer_id, status, created_at).
  • Leading wildcard (LIKE '%data%') cannot use a normal index. Use full-text or trigram index.
  • Trade-off: indexes speed reads but slow inserts and updates, and use storage.

18. System Design Fundamentals and Architecture Styles

  • Layered: presentation, service, domain, data layers. Dependencies go downward.
  • Client-server: clients send requests, servers respond.
  • Event-driven: components react to events through a broker.
  • Microservices: small services, each owns its data and deploys alone.
  • SOA (self study): services connected through an enterprise bus (ESB).
  • Trade-off: monolith is simple to run; microservices scale and deploy independently but add complexity.

19. REST API Design

  • Model resources as nouns: /orders, /orders/{id}/items.
  • Real-world API case studies (self study): study how large public APIs name resources, version and paginate.
  • GET read, POST create, PUT replace, DELETE remove.
  • Idempotent: GET, PUT, DELETE (repeat gives same result). POST is not.
  • Versioning: /v1/ in URI or a header, so old clients keep working.
  • API Gateway: single entry point for authentication, rate limits and routing.

20. Scalability and Performance

  • Vertical scaling: bigger machine (limited, single point of failure).
  • Horizontal scaling: more machines (needs stateless design).
  • Load balancing: L4 routes by IP and port; L7 routes by URL and headers.
  • Caching: cache-aside, write-through, write-around, write-back. Watch for stampede (use mutex or XFetch).
  • CDN: edge servers near users cache static files.
  • Database scalability: read replicas, sharding, caching.

21. UI Design Approaches

  • Traditional HTML (server-rendered): each action reloads the page. Simple, low client code.
  • React (SPA): the browser builds the page from JSON. Rich interaction, larger bundle.
  • HTMX: HTML attributes send requests and swap parts of the page with server HTML. Small JavaScript.

22. Design Patterns (Syllabus)

Creational

  • Factory: creates the right object without the caller knowing the class (PDF, CSV or JSON exporter).
  • Singleton: only one object with one global access point (config manager). Drawback: hard to test.

Structural

  • Adapter: translates one interface to another (legacy inventory to new order module).

Behavioral

  • Observer: subject notifies observers on change (order status to customer and dashboard).
  • Strategy: interchangeable algorithms behind one interface (payment by UPI, card or wallet).
  • MVC: Model holds data and rules, View shows data, Controller handles input.

23. Architecture Quality Attributes

  • Performance: response time and resource use.
  • Scalability: handling more users or data.
  • Maintainability: ease of change and fixing.
  • Security: authentication, authorization, input validation, encryption.
  • Reliability: keeps working when parts fail (transactions, retries, health checks).

24. Deployment Diagram and Containerization

  • Node: hardware or runtime (server, device). Artifact: deployed file.
  • Communication path: label with protocol, such as HTTPS or SQL.
  • Containers: package app and dependencies as one image. Same image runs on laptop, test and production.
  • Keep configuration (database address, secrets) outside the image.

25a. Case Study: Persistence Layer

  • Example: E-commerce or library system.
  • Entities: Customer, Product, Order, Book, Member, Loan.
  • Layers: entity classes, repositories (interfaces), DAO or ORM implementation, database.
  • Keep the schema in 3NF, add indexes for common searches, use transactions for orders and stock.

25. Integration of Object Model, Database, API, UI and Deployment

  • Class model gives business rules and objects.
  • Map classes to tables with keys and constraints.
  • Repositories and services use the mapped objects.
  • API exposes services with clear error responses (400, 401, 404, 500).
  • UI calls only the API. Deployment places each part on nodes.
  • Test each layer, then the full flow end to end.

End-to-end system design (self study)

  • Start from the object model, then the database, API, UI and deployment, in that order.
  • Keep each step traceable to a requirement.

26. AI Tools in Design Work

  • Assignment validation: give the rubric and ask for a score with reasons, then check by hand.
  • Design review: use a checklist (patterns, quality attributes, security, deployment, integration).
  • Documentation: check generated text against diagrams, code, requirements and ADRs.
  • ADR writing: draft the sections, then a human confirms the reasons and alternatives.
  • Never accept AI output without human review.

27. Design Steps for a System

  1. Understand requirements: list actors and use cases (use case diagram).
  2. Find domain classes and their responsibilities (CRC cards).
  3. Draw the class diagram and assign responsibilities with GRASP and SOLID.
  4. Show key behaviour with sequence, activity and state diagrams.
  5. Choose architecture style and record decisions in ADRs.
  6. Map classes to database tables, normalize to 3NF, add indexes.
  7. Design the API (REST resources and methods) and the UI approach.
  8. Plan scaling, caching, security and reliability.
  9. Draw the deployment diagram and containerize.
  10. Review the design against requirements and quality attributes.
